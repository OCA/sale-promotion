Partner Referral

Personal referral links for partners — customers, influencers, ambassadors.

Use cases:

  • Classic referral: a customer shares their link; the friend’s first order gets a discount.
  • Influencer code: an ambassador’s link tracks and discounts the sales they drive.
  • Tracking only: a referral program without rewards keeps pure attribution — referred_by_id on orders, no discount.

How it works:

  • Each partner can get a unique referral code and a shareable link, from the referral program’s “Generate Referral Code” button, the partner form/list (for a default referral program), or the partner’s portal (same).
  • The code is a “Discount Code” program, so it works everywhere promo codes do: sale order coupon wizard and eCommerce promo box. In POS it applies automatically on the carried-over sale order; typing a referral code at the POS till needs a pos_loyalty extension.
  • Each referral program owns one internal “Conditional Rule” with a random code. It is plumbing, not a user code: typed referral codes alias it behind the scenes, and it refuses to apply on orders without a referrer. Do not share or edit it — put shared conditions on it instead.
  • Referral links land on a configurable base URL with ?referral=<code>, captured on any page (session + cookie): attribution can survive navigation, logins and browser restarts.
  • Orders record the referrer in referred_by_id, whether the code came from the link or was typed at checkout.

Configuration

  1. Enable loyalty: Sales > Settings > Pricing > “Promotions, Loyalty & Gift Card”.
  2. Create the referral program from the Referral tile (Sales > Products > Discount & Loyalty > New). It is a “Discount Code” program with a preset reward; adjust the reward to taste.
  3. In Sales > Settings > “Customer Referrals”, select the program as “Referral Program” and set “Referral Base URL” (default /; any Odoo page works — a landing page, /appointment, etc.).
  4. The selected program shows a “Default Referral Program” ribbon on its form, a “Referral Codes” smart button listing minted codes, and a “Generate Referral Code” button.
  5. To let partners generate their own link, drag the “Invite a Friend” building block (Social category) onto a website page in the editor. It is only rendered for logged-in users.

With sale_loyalty_order_count_condition installed, the program gains an “Order Count Condition” field — set it once at program level (e.g. “Customer’s first order”) and every minted code shares the policy. It relies on partner identity: guest checkouts create fresh partners, so repeated anonymous visitors may still pass a “first order” check.

Usage

  • Staff creates codes per partner on the partner form (Sales & Purchase > Referral > “Generate Referral Code”; the code, shareable link and referred count show there), in bulk via the partner list Action > Generate Referral Code (uses the default referral program).
  • Partners can also opt in themselves through the “Invite a Friend” block placed on a website page, where they see the copyable link, the bare code and the count of visitors who converted.
  • The referral program form shows every created code under the “Referral Codes” smart button, each linked to its referrer.
  • Friends open the link; their eligible order gets the configured reward — automatically where an integration applies it, or by typing the code in any promo code field. Either way the order records referred_by_id.
  • Failed applications never block a checkout; they are noted on the order’s chatter instead.

Known issues / Roadmap

Status: shipped

Decisions

  • Referral codes live as with_code rules on a promo_code program — the only loyalty type where one code serves unlimited distinct consumers.
    • Rejected: loyalty.card per referrer — card partner_id means holder-as-spender, and its point entries are zeroed when the spender differs; points balance is finite, referrals need unlimited uses.
    • Rejected: program_type='referral' — every program_type branch in Python and POS JS would need extending; a ‘referral’ template tile gives the same UX with zero behavioral surface.
  • Participation is a loyalty.referral link record (partner × program, mirroring loyalty.card’s shape) owning the promo rule. 2026-10 — supersedes “rejected: dedicated referral.code model”: the model is not a duplicate registry but the referral-domain object; the rule stays pure promo plumbing. Gives multi-code/multi-program per partner for free.
  • ?referral= query param captured on ir.http._post_dispatch — works on any landing page, survives navigation; replaces the dedicated /referral/<code> route idea. UTM is kept as optional analytics only.
  • Code generation is opt-in (portal button, partner Action menu, program button). 2026-10 — supersedes lazy mint-on-read.
  • Referral program is selected in Sales Settings (ir.config_parameter). 2026-10 — supersedes the ``is_referral`` flag + ``referral_base_url`` field on ``loyalty.program``: explicit selection beats “first flagged wins”.
  • One rule per customer carries referrer_id — the code registry and the owner link in one place. _try_apply_code stamps referred_by_id on orders, covering manually typed codes too.
  • Application failures post a chatter note on the order rather than only logging; no exception activity (too much noise for expected outcomes).
  • Seed program via XML + post-init hook for params/reward — the reward’s discount product needs conditional handling for website_sale’s required publish_date, which XML cannot express portably.

Plan

  • Iteration 1: generic engine (codes, links, capture, portal, apply helper).
  • Iteration 2: surface bridges (website_sale cart, appointment/POS layer in brb_appointment_referral).
  • Iteration 3: referrer reward (issue the referrer a next_order_coupons/ eWallet card on friend conversion — loyalty.card is the right model for that direction).
